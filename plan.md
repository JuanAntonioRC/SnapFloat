### Critical findings from live debugging (do not re-litigate, verified empirically)

- **XGrabKey does not work AT ALL in this GNOME/Wayland session, for ANY modifier combo** — not just Super. Verified three ways: (1) real physical key presses (user tried Shift+Alt+S several times, with and without an XWayland window of ours focused), (2) a synthetic `XTestFakeKeyEvent` injection (built a tiny standalone C test binary linking `-lX11 -l:libXtst.so.6`, confirmed it runs and resolves keycodes correctly), (3) an independent polling fallback (`g_timeout_add` every 200ms calling `XPending` directly, bypassing `g_unix_fd_add` entirely, to rule out a bug in our own event-loop wiring). All three: **zero X11 KeyPress events ever arrive** at our grab, despite `XGrabKey` reporting success (no `BadAccess`). Root cause: Mutter (GNOME's Wayland compositor) simply does not forward XWayland passive-grab key events to the client unless something else is going on we don't yet understand — this is a compositor-level input-routing limitation, not a bug in `GlobalHotkey.swift`.
- **The GlobalShortcuts portal rejects the app outright**: `gdbus call ... org.freedesktop.portal.GlobalShortcuts.CreateSession ...` → `GDBus.Error:org.freedesktop.portal.Error.NotAllowed: An app id is required`. This portal requires the caller to be sandboxed (Flatpak or Snap) so `xdg-desktop-portal` can resolve an app ID via cgroup/confinement info. SnapFloat today is an unsandboxed native binary (`.deb` / manual build) — the portal call fails before ever reaching Mutter's shortcut-binding UI, regardless of which key combo is requested.
- **No "GNOME on Xorg" session available** on this machine (`/usr/share/xsessions` doesn't even exist) — so switching the user's login session to plain X11 (which would make raw `XGrabKey` work normally, no compositor involved) is not an option here.
- **Conclusion**: as packaged today (native `.deb`), there is no working mechanism for a true global keyboard shortcut in this environment. Two viable paths discussed with the user:
  (a) Package as Flatpak or Snap → satisfies the portal's sandboxing requirement → portal *should* then be able to negotiate the shortcut with Mutter properly (this is the officially sanctioned mechanism, unlike raw XGrabKey). **Not yet empirically verified** — plausible based on how the portal's app-id resolution is designed (it has code paths for both Flatpak and Snap confinement), but never tested end-to-end.
  (b) Read raw kernel input (`/dev/input/eventX`) below the compositor. Works regardless of sandboxing/session type, but needs one-time `usermod -aG input` + relogin, and can't consume/block the keystroke from also reaching the focused app. Not started, user did not pick this path.
- User picked **(a), specifically Snap** (not Flatpak) after a discussion of tradeoffs (Snap vs Flatpak are ~equivalent for this purpose; Snap is more natively Ubuntu-flavored).

### Known packaging implications discussed with the user (already communicated, don't re-derive)

- Snap/Flatpak install alongside the `.deb` with zero conflict — separate install locations, separate config storage. Only real overlap: same D-Bus app ID (`com.snapfloat.SnapFloat`), so running both at once would just re-activate whichever grabbed the name first (single-instance behavior) — not a real problem, just can't meaningfully run both simultaneously.
- Expect resting memory to land somewhat higher than the ~17-19MB native figure once sandboxed — extra `bwrap`-equivalent + a per-app D-Bus filtering proxy process, plus the Swift runtime (libswiftCore, Foundation, ICU) has to be bundled with the app itself rather than shared via a common runtime the way GTK4 is. Rough expectation communicated to the user: ~20-30MB USS at rest under Snap, still fine, just not free.
- All of the memory-optimization work (lazy GTK init, malloc tuning, GSK_RENDERER=cairo) carries over unchanged into the Snap build — it's app-level code, packaging-agnostic. Just need to remember to set the same env vars in the snapcraft.yaml's `command`.
